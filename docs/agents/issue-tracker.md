# Issue tracker: GitHub

Issues and specs for this repo live as GitHub issues of `FrankDrebin893/hojt-audio`. This file is
what the installed Matt Pocock skills (`.claude/matt-pocock-skills/README.md`) read; the repo's
own flow (states, approval, labels) is in `CLAUDE.md`, "How work flows", and wins wherever the two differ.

## Conventions

- **Tools.** Locally use the `gh` CLI. In a cloud session `gh` is not signed in and GraphQL is
  blocked: use the GitHub MCP tools (`issue_read`, `issue_write`, `add_issue_comment`,
  `sub_issue_write`) and `gh api -X GET search/...` for search
- **Create an issue** with `/issue`, which fills the same fields as the issue forms. Never file
  by hand with a bare `gh issue create`
- **Read an issue**: `gh issue view <number> --json number,title,body,labels,comments`
- **Sub-issue**: a child body starts with `Parent: #<parent>` (`/next` reads it); link it as a
  GitHub sub-issue where possible. A wayfinder ticket uses `Map: #<map>` instead, never `Parent:`
- **Blocking**: a sentence `Waits for #<n>` in the body; the Builder skips the issue while that
  issue is open
- **Labels**: exactly one `state:*` label (`idea`, `spec`, `approved`, `building`, `review`), plus
  `kind:*`, `plugin:*` / `app:piano`, `area:*`. A skill never sets `state:approved`: only the
  repository owner does. `needs:engineer` marks an issue awaiting an engineer decision
- **Comments** end with the footer `---` and `_Generated by [Claude Code](https://claude.ai/code)_`,
  and never name a person
- **Close** with an explanation comment first; closed means merged or turned down

## When a skill says "publish to the issue tracker"

Use `/issue` for an idea, `/spec` to put a spec on an issue. Do not use the Pocock skills that
publish tickets (`to-spec`, `to-tickets`, `triage`): they are not installed, the repo's own
skills do that job.

## When a skill says "fetch the relevant ticket"

Read it as in **Read an issue** above, with its comments (the spec, and the latest "Progress" comment).
